# Gap Analysis 03 — Infrastructure, CI/CD & Operational Readiness

**Domain:** `infrastructure/`, `.github/workflows/`, `docker-compose*.yml`, Dockerfiles, database migrations, observability, background jobs, environment config.
**Method:** files read directly; the four priority-setting claims (dead CD trigger, missing migrations, entity registration, health-path mismatch) independently re-verified. `Verified` = read in code. `Inferred` = runtime effect deduced from code.
**Date:** 2026-09-15 · **Branch:** `64-frontend-design-deliverables` after merging `develop` (`21eb15d`).

---

## Summary

1. **There is no infrastructure as code.** `infrastructure/` holds an nginx config, a Prometheus config and Grafana stubs; the 13 KB Terraform setup guide describes modules, environments and an S3 state backend that do not exist.
2. **Both CD workflows are dead at their first job**: they call `ci.yml` as a reusable workflow, but `ci.yml` declares no `workflow_call` trigger. Production additionally needs a changelog config and `CHANGELOG.md` that are absent.
3. **A production database cannot take an order.** No migration creates the `payments.*` or `analytics.*` tables; the root TypeORM config registers only the events/tickets entities with no `autoLoadEntities`; nothing runs migrations on deploy; and the migration CLI cannot run inside the production image. Development is masked by `synchronize: true`.
4. **The health-check contract disagrees with itself**: the backend serves `/api/health` returning `{status, timestamp}`; prod compose, both CD workflows and the smoke tests call `/health` and expect `.database.status`. The frontend image has no `curl`, so its healthcheck always fails.
5. **The backend is single-instance only**: in-memory webhook dedupe and five unlocked cron jobs, against docs that target N Fargate tasks. Observability is default text logging.

## What is solid

- **Backend production Dockerfile** is correct in shape: multi-stage, `npm ci` in the builder, prod-only deps in the runner, non-root `nestjs` user, `dumb-init`, `HEALTHCHECK` on the right path (`backend/Dockerfile:5-64`).
- **Frontend Dockerfile** correctly targets Next's `standalone` output and runs as non-root.
- **The CI job graph is well structured**: lint → architecture fitness → unit (both packages) / integration (real Postgres 15 + Redis 7, migrations applied) / e2e / build / Docker build with cache / security scan / quality gate. Frontend tooling (`type-check`, `format:check`, `vitest --coverage`, Playwright) is real.
- **Local compose is rich and health-gated**: Postgres 15.4 with init scripts, Redis AOF, pgAdmin, Maildev, LocalStack for S3/SES/SNS, `depends_on: service_healthy`.
- **Config validation exists** (Joi, `abortEarly: false`, `JWT_SECRET` required) plus global throttling, exception filter and timeout interceptor.
- **Migrations that exist are hand-written SQL with schemas, indexes and `down()`**, and the most recent features (commission override, check-in staff) shipped *with* migrations.
- **CD design intent is sound once unblocked**: ECR tagging by SHA/semver, Cosign signing, a GitHub `environment` approval gate, blue/green ALB listener swap with automatic rollback.

## Fix order

1. **I-03 · I-04 · I-05** together — *a production database that can take an order* — proven by a fresh-database integration test that creates an order through the payments repository.
2. **I-02** — one line in `ci.yml` plus two committed files, and CD becomes runnable.
3. **I-06 · I-08 · I-07** — the deploy would fail its own health checks and the frontend would call the wrong URL.
4. **I-09** before running more than one task; **I-10** before the first incident you cannot diagnose.
5. **I-01** is a strategic decision: real Terraform, or an honest "manually provisioned" label on the docs. Either is fine; the current state — a setup guide for infrastructure that does not exist — is not.
